# AGENTS

## Project Context

- Project: Helm Charts (`github.com/maxmorhardt/charts`)
- Language: Helm templates (Go templating over YAML), plus Python for the CronJob charts
- Purpose: Chart source for every application deployed to the cluster. CI publishes each chart as an OCI artifact to `ghcr.io/maxmorhardt/charts`; Argo CD deploys it from an `Application` in the `k8s` repo.
- Target environments: A self-hosted K3s cluster using Gateway API, kube-prometheus-stack, and Argo CD.
- Related repos: `k8s` (the Argo CD Applications that consume these charts), `workflows` (the shared `ci-helm` and `cd-argocd` workflows), plus the app repos whose images these charts deploy.

**This repo holds chart source only. No deployment state lives here.**

## Repository Layout

- `charts/<name>/` - one self-contained chart per directory.
  - `Chart.yaml` - name, description, `type: application`, and `version` (owned by release-please).
  - `values.yaml` - the full default value set. Charts are not installed with custom values in production, so defaults here **are** the production config.
  - `templates/` - manifests. Common set: `deployment.yaml`, `service.yaml`, `httproute.yaml`, `backendtrafficpolicy.yaml`, `hpa.yaml`, `pdb.yaml`, `servicemonitor.yaml`, `prometheusrule.yaml`, `_helpers.tpl`.
  - `DEPENDENCIES.md` - external things the chart assumes exist (gateway, TLS secret, DNS record, backing services).
  - `CHANGELOG.md` - generated by release-please.
- `charts/cloudflare-cidr/`, `charts/cloudflare-ddns/` - CronJob charts shipping a Python script mounted via ConfigMap.
- `charts/maxstash-gateway/` - Gateway API infrastructure for the `maxstash.io` gateway (`GatewayClass`, `Gateway`, `EnvoyProxy`, client traffic policy, HTTPS redirect). Not an app.
- `.github/workflows/ci-chart.yml` - on PR, discovers every chart directory and validates each in a matrix. On tag push, packages and pushes one chart, then bumps its `targetRevision` in `k8s`.

## Core Principles

1. Source only, never state
   - Charts are never installed with `helm install` or `helm upgrade` against the cluster from this repo.
   - `kubectl` is for inspecting what Argo deployed, nothing more.
2. Defaults are production
   - There is no separate prod values file. What is in `values.yaml` is what runs.
3. Production posture is not opt-in
   - Application charts carry non-root `securityContext` with `readOnlyRootFilesystem`, `emptyDir` volumes for every writable path, startup, readiness, and liveness probes, requests equal to limits, pod anti-affinity, an HPA, and a PDB.
   - Start a new chart from an existing one so none of this is silently dropped.
4. Observability ships with the chart
   - A metrics exporter sidecar where the app does not expose Prometheus metrics itself, plus `ServiceMonitor` and `PrometheusRule`.
5. Gateway API, not Ingress
   - Routing is `HTTPRoute` with a `parentRef` to the `maxstash` gateway in `envoy-gateway-system`. Rate limiting goes in the `BackendTrafficPolicy`.
6. Consistent naming across charts
   - Every chart defines the same `_helpers.tpl` set: `app.name`, `app.fullname`, `app.chart`, `app.labels`, `app.selectorLabels`.
   - Dashboards and PrometheusRule expressions match on `app.fullname`, so renaming a helper breaks alerting silently.
7. Versions are pinned and committed
   - Both `targetRevision` and `image.tag` in `k8s` are exact and both are written by CI, so every rollout is a reviewable, revertable commit.

## Agent Instructions

- Make the smallest safe change that solves the requested problem.
- Set `fullnameOverride` in `values.yaml` so resource names stay stable regardless of release name.
- **`image.tag` is `''` in `values.yaml`.** The real tag is supplied as a Helm parameter by the Argo CD `Application` in `k8s`, committed there by the app repo's release workflow. Never pin a tag here.
- Alert rules live in `values.yaml` under `metrics.prometheusRule.rules` and are templated, so they can reference `{{ include "app.fullname" . }}`. Keep `expr` blocks as `|` literals; the surrounding Helm quoting matters.
- Alert labels follow `severity` (`warning` or `critical`), `component` (the app), and `layer` (`frontend` or `backend`).
- Gate optional resources behind an `enabled` flag (`route.enabled`, `hpa.enabled`, `pdb.enabled`, `metrics.serviceMonitor.enabled`) so a chart renders without them.
- Update `DEPENDENCIES.md` when a template starts depending on something outside the chart.
- Never hand-edit `Chart.yaml` `version`, `CHANGELOG.md`, or `.release-please-manifest.json`.
- Copy `_helpers.tpl` verbatim when adding a chart rather than inventing new template names.

## New Chart Checklist

1. Copy the closest existing chart directory and rename it. Keep `_helpers.tpl` as-is.
2. Set `Chart.yaml` `name`, `description`, and `version: 0.1.0`. Release-please owns the version from there.
3. Set `fullnameOverride`, `image.repository`, hostnames, resources, and alert `component` and `layer` in `values.yaml`.
4. Write `DEPENDENCIES.md` listing required and optional external dependencies.
5. Add the chart to `release-please-config.json` under `packages` with `"release-type": "helm"` and a `component` matching the directory name. **Without this the chart is never released.**
6. Add the matching Argo CD `Application` in the `k8s` repo under `argocd/apps/`. **Nothing deploys until that exists.**

CI discovers chart directories automatically, so no workflow change is needed.

## Testing Guidance

Rendering is the test. Run what CI runs before pushing:

```bash
helm lint ./charts/squares --strict
helm template <release-name> ./charts/squares
helm template <release-name> ./charts/squares -f custom-values.yaml
```

- CI validation goes through `maxmorhardt/workflows/.github/workflows/ci-helm.yml`: `helm lint --strict`, `helm template`, and kubeconform against the rendered output.
- **A template that renders invalid Kubernetes YAML fails on kubeconform, not on lint.** Passing `helm lint` alone proves very little, so always render and inspect the output.
- Render with the optional flags both on and off. A chart that only renders with everything enabled will break the first time someone disables a feature.
- For alert rule changes, check the rendered `PrometheusRule` and confirm the `expr` interpolated `app.fullname` correctly rather than emitting a literal.

## Dependency Checklist

Before adding a chart dependency or a new templated resource, verify:

- Can this be expressed with the resources the chart already renders?
- Does it need a CRD that may not exist at sync time? Argo retries, but a hard dependency belongs in `DEPENDENCIES.md`.
- Does it require a new external prerequisite (gateway, secret, DNS record)? Document it.
- There are deliberately no subcharts, no umbrella charts, and no `Chart.lock` here. Adding a `dependencies:` block is a significant change, so justify it.
- For the Python CronJob charts, prefer the standard library. Anything added to `requirements.txt` is installed at pod start.

## Versioning and Deployment

- Release-please with `include-component-in-tag` and `/` as the tag separator, so tags look like `squares/1.0.2`. Each chart directory is an independent package with its own changelog.
- **Merging to `main` does not deploy.** The release PR merging and its tag landing is what publishes the OCI chart and commits the new `targetRevision` into `k8s`.
- A chart change with no image change still ships this way. Bumping `cloudflare-cidr`'s Python script is a chart release, and that release is the deploy.

## Commit Tags

Conventional commits, enforced on PR titles by `pr-title.yml` and consumed by release-please. The type determines the release, so it is a functional choice, not a stylistic one.

- `feat`: New chart capability. Cuts a minor release for that chart.
- `fix`: Corrects a wrong or unsafe rendered manifest, a broken alert expression, or a script bug. Cuts a patch release.
- `refactor`: Template restructuring that renders identically.
- `chore`: Maintenance that does not change rendered output, including routine dependency bumps.
- `ci`: Workflow or release automation changes.
- `docs`: `README.md` or `DEPENDENCIES.md` only.

Scope should be the chart name.

Example commit subjects:

- `feat(squares): add rate limit to httproute`
- `fix(cloudflare-ddns): handle empty zone response`
- `chore(maxstash): align resource requests with observed usage`
- `ci: discover chart directories for the validation matrix`

## Non-Goals for Routine Changes

- Running `helm install` or `helm upgrade` against the cluster from this repo.
- Pinning `image.tag` in `values.yaml`.
- Hand-editing `Chart.yaml` versions, changelogs, or the release-please manifest.
- Adding a chart without a `release-please-config.json` entry and an Argo CD `Application` in `k8s`.
- Dropping probes, security context, PDB, or anti-affinity from an application chart to simplify it.
- Renaming `_helpers.tpl` templates, which silently breaks dashboards and alerts.
